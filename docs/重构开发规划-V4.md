# V4 重构开发规划：异步事件驱动 + 全链路可观测

> 依据《专项考核：V2 下单流程异步事件驱动重构与全链路可观测性实战》（V4.0，2026/08/03）
> 项目目录：`E:\IntelijWorkSpace\AiWorkSpace\import-order`（在现有 V2 上重构，不重写规则引擎）

---

## 一、现状与目标

现有 V2 主链路为同步阻塞：上传 → 解析 → 规则 → 校验 → 逐行写库，一次请求完成。重构目标：

- 上传即返回（P95 ≤ 1s，返回 task_id）；
- 10,000 行全链路 ≤ 60s（≥ 10,000 单/分钟）；
- 批量校验 + 批量写入（禁止逐行查询/INSERT）；
- 行级错误、批次性能日志、traceId 全链路、监控看板；
- Outbox 可靠投递 + 处理单元幂等 + 失败重试 + 卡死恢复；
- SKU 校验降级（超时 3s 自动降级并显式提示）。

## 二、关键架构决策（含理由）

### 2.1 队列选型：PostgreSQL 事务性 Outbox 即队列（DB-based Queue）

考纲推荐 BullMQ+Redis/Upstash，但本项目当前仅有 Neon 连接串，且 Vercel Hobby 无常驻 Worker。选择 **event_outbox（事务性发件箱）作为可靠事件存储 + import_task_batches 作为可认领工作单元**，Dispatcher/Worker 以「Serverless Consumer（pump）」模式消费。理由：

- 满足强制项「任务创建与批次事件同事务」与「禁止只 queue.add 无本地可靠记录」；
- `SELECT ... FOR UPDATE SKIP LOCKED` 认领批次，天然并发控制 + 防重复消费；
- 无需额外 Redis 凭据，连接池压力可控（Neon HTTP 无状态驱动）；
- 同时提供 `scripts/worker.mjs` 本地常驻 Worker（循环 pump），生产可部署到 Railway/Render（README 说明）。

### 2.2 Worker 驱动模型（Vercel 兼容）

- 上传 API 用 `context.waitUntil` 在响应返回后立刻触发第一次 pump（解析单元）；
- 前端任务页 1.5s 轮询 `GET /api/import-tasks/:id`，每次轮询顺带 `waitUntil(pump)` 推进队列；
- 每次 pump 在时间预算内（≈8s）顺序处理若干处理单元；多 pump 并发由 SKIP LOCKED 协调；
- 本地/压测可用 `scripts/worker.mjs` 常驻循环 pump，提高并发。

### 2.3 处理单元设计

- 解析单元（unit_000）：读原始文件 → SheetJS 解析 → 复用 V2 规则引擎 → 行暂存 `import_task_rows`（单次多行 INSERT）→ 创建 N 个批次单元 + Outbox 事件 → 更新 total_rows/total_batches；
- 批次单元（unit_001..N）：**1000 行/批**，10,000 行 = 10 批；
- 每批：读暂存行 → 批量 SKU 校验（`sku_code = ANY(...)`，3s 超时→降级）→ 行级校验 → 成功行批量 UPSERT（waybills + waybill_items，两次多行 INSERT）→ 失败行写 import_task_errors → 写 batch_performance_log → 原子聚合任务进度。

### 2.4 容量推导（10,000 单/分钟）

| 项 | 设计/推导 |
| --- | --- |
| 数据量 | 10,000 行压测文件 |
| 处理单元 | 1 解析单元 + 10 批次单元（1000 行/批） |
| 单批耗时（实测目标） | 读暂存 ~50ms + SKU 批量校验 ~100ms + 批量写 ~200ms + 开销 ~150ms ≈ 0.5s |
| 并发 | pump 并发 2-4（轮询+waitUntil），SKIP LOCKED 协调 |
| 总耗时推导 | 解析 ~1.5s + 10 批 ×0.5s / 并发2 ≈ 2.5s + 调度间隔 ≈ **5-15s** ≪ 60s |
| DB 压力 | 每 pump 单连接；每批 1 次 SKU 查询 + 2 次多行写入；峰值连接 ≤ 并发 pump 数 |
| 失败成本 | 单批失败仅重试该批（retry_count≤3）；dedup_key 唯一索引防重复入库 |

### 2.5 幂等与去重

- import_task_batches UNIQUE(task_id, unit_id)；认领时 `FOR UPDATE SKIP LOCKED`，已完成直接返回；
- waybills 增加 `dedup_key`（external_code|sku_code|row_number）唯一索引，UPSERT ON CONFLICT DO UPDATE；
- 进度不逐次累加：任务进度由「已完成批次汇总」原子重算，重试不重复累计。

### 2.6 降级策略

SKU 批量查询 `Promise.race` 3s 超时或连接失败 → degraded=true：跳过 SKU 主数据校验（仅本地格式校验），写 trace 事件 ImportTaskDegraded + 任务标记，任务详情页显式黄色告警；记录未校验行数（skus_unverified_rows）；新任务自动恢复。

## 四、接口清单

| 接口 | 说明 |
| --- | --- |
| POST /api/import-tasks | 上传文件+rule_id，同事务建任务+Outbox，≤1s 返回 task_id |
| GET /api/import-tasks | 任务列表 |
| GET /api/import-tasks/:id | 任务进度（轮询顺带 pump） |
| GET /api/import-tasks/:id/errors | 行级错误（batch/error_code/分页） |
| GET /api/import-tasks/:id/batches | 批次性能 |
| GET /api/traces/:traceId | Trace 时间线 |
| GET /api/traces?query= | 按 task/文件/批次/行号/错误码搜索 |
| GET /api/import-monitor/summary | 吞吐/积压/阶段耗时/错误分布 |
| POST /api/internal/pump | Dispatcher+Worker 推进（waitUntil/worker 调用） |
