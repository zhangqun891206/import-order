# 重构假设说明（V4 异步事件驱动）

> 随源码提交，覆盖考核第六章模块十一的 12 项要求。

## 1. 为什么选择异步事件驱动，而不是继续同步处理
同步链路在一次 HTTP 请求内完成解析+校验+逐行写库，10,000 行即使每行 200ms 也需 30 分钟，远超 Vercel Serverless 单次请求时限，且逐行写库会打满连接池。异步事件驱动把「上传」与「处理」解耦：上传只创建任务并立即返回 task_id（P95≤1s），后台 Worker 分批消费，可横向扩展、可重试、可观测。同步更简单可靠的场景是小文件（几十行）、低并发、无需进度与失败定位——此时同步减少组件、事务边界清晰，V2 的「旧版同步导入」即保留用于该场景。

## 2. 处理单元大小如何设计，为什么
解析单元（unit_000）负责读文件+规则引擎+行暂存；数据按 **1000 行/批** 切分为批次单元（10,000 行=10 批）。选 1000 的理由：单批 DB 写入量可控（一次多行 INSERT ~1000 行），失败重试范围小（最多重放 1000 行），且 10 个批次可被多 Worker 并行消费。过大（如 5000）会放大重试成本与单函数内存；过小（如 100）会增加调度与连接开销。

## 3. Worker / Consumer 容量规划
采用「Serverless Consumer（pump）」+ 可选常驻 Worker（scripts/worker.mjs，生产可部署 Railway/Render）。每次 pump 在时间预算内用 `SELECT ... FOR UPDATE SKIP LOCKED` 认领处理单元，天然限流与防重复。压测用 2~4 个并发 Worker。峰值 DB 连接数 ≈ 并发 Worker 数（Neon HTTP 无状态驱动，每请求单连接），不会耗尽连接池。

## 4. 10,000 单/分钟性能推导
- 数据量：10,000 行。
- 处理单元：1 解析 + 10 批次。
- 单批耗时（同区域部署实测目标）：读暂存 ~30ms + SKU 批量校验 ~30ms + 批量 UPSERT ~60ms + 物品行 ~40ms + 开销 ~40ms ≈ 200ms。
- 并发 2：10 批 ×200ms / 2 ≈ 1s；解析 ~1~2s；调度间隔 ~数秒。合计 ≪ 60s。
- 高延迟网络（本地跨境 ~1s/查询）下，通过批内 `Promise.all` 并行化把每批往返轮数压到 ~5 轮，10 批/并发2 ≈ 25~40s，仍 ≤60s。

## 5. 数据库连接池和 Worker 并发如何控制
Neon 使用 HTTP serverless 驱动（无长连接池），每次查询独立 HTTPS 请求；Worker 并发由 pump 数控制（压测 2~4），`SKIP LOCKED` 保证一个处理单元只被一个 Worker 认领。批内独立查询用 `Promise.all` 并行，减少串行往返。

## 6. Outbox 如何避免「任务创建成功但消息丢失」
任务、解析单元、Outbox 事件在**同一条 SQL（CTE）= 单事务**中写入；Dispatcher 轮询 event_outbox 把 pending 事件标记 sent；投递失败 retry_count+1 并设 next_retry_at 延后重试，超过上限标记 failed。宕机恢复后 Dispatcher 继续投递未 sent 的事件，不丢消息。

## 7. 处理单元 Job 如何做到幂等
- import_task_batches UNIQUE(task_id, unit_id)；认领用 `FOR UPDATE SKIP LOCKED`，已完成（done）的单元再次消费直接跳过。
- 行暂存 `ON CONFLICT (task_id,row_number) DO NOTHING`。
- 运单 UPSERT 基于稳定业务键 dedup_key(external_code|sku_code|row_number) `ON CONFLICT DO UPDATE`。
- 物品行「先清后插」；错误明细「先清本单元再写」。
- 任务进度由「已完成批次汇总」原子重算，重试不重复累计。

## 8. 部分行失败时为什么允许成功行继续入库
一行数据错误（如 SKU 不存在、电话格式错）是数据质量问题，不应阻断整批其它正确数据。成功行入库保证业务吞吐，失败行写入 import_task_errors 并提供行号/字段/原始值/修复建议，用户可修复后重导。任务状态置 partial_success，明确区分。

## 9. SKU 校验降级的触发条件和风险提示
触发：SKU 主数据批量查询 3s 超时（Promise.race）或连接短暂失败。降级后跳过 SKU 主数据校验，仅做本地格式校验；任务记录 degraded=true 与 unverified_sku_rows；写 ImportTaskDegraded trace；任务详情页显式黄色告警「⚠️ SKU 校验已降级…需后续复核」。新任务自动恢复正常校验。是否补校验：建议对降级任务生成「待复核」清单异步补校验（本次记录清单，不阻塞主链路）。

## 10. 错误日志中敏感数据如何脱敏
import_task_errors.raw_value 写入前脱敏：手机号保留前3后4（138****0000），地址保留前6后4，其它超长截断。前端展示与导出均基于脱敏值；排障所需行号/字段/错误码不敏感，保留。

## 11. 压测数据如何生成、如何清理
`scripts/seed-data.mjs`：清理 `SKU_%` 主数据后批量插入 20,000 条（SKU_00001~20000）；生成 test-data/10000-orders.xlsx（10,000 行，SKU 随机抽取并注入 ~1% 非法行验证错误定位）；创建压测解析规则。可重复执行（先清理再重建）。清理：`DELETE FROM sku_master WHERE sku_code LIKE 'SKU_%'`；任务/错误/性能日志按保留期归档清理（见下）。

## 清理/归档策略
- event_outbox：sent 且超过 7 天归档/删除；failed 保留 30 天待人工处理。
- batch_performance_log / trace_events：保留 30 天，超期归档到冷存储。
- import_task_rows：任务完成 24 小时后清理（已入库运单为准）。
- import_task_errors：保留 90 天供用户修复重导。
